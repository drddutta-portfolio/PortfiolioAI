## Four direct-source metric definitions and identified compatibility defect
All four M1–M4 records were inserted via normal data-row INSERT (no schema migration) and independently read back as `PERCENT`, `NUMERIC`, direct source-only, reviewed selection:
- NIM_TTM: exact `TRAILING_FOUR_QUARTERS` token; reporting start and end ISO dates; source must expressly certify trailing-4Q NII/average interest-earning assets; no annual NIM substitution.
- CET1_RATIO: exact `REGULATORY_AS_OF` token, `period_start=period_end` at disclosure regulatory as-of date, explicit Basel III CET1 and regulatory perimeter.
- CAPITAL_ADEQUACY_RATIO: same regulatory token/date representation, direct Basel III total CRAR and scope; not Tier 1-only or CET1-only.
- ROA_ANNUAL: exact `YEAR`, full-year start/end ISO dates and audited annual direct source.
The existing `validateObservationSeries` compares `row.period_type` string to `definition.period_type` exactly, so these tokens are syntactically supported, **provided reviewed source rows match them**. The canonical materializer also requires reviewed evidence before M1–M4 normal observations can be accepted; absence of a valid review is a hard stop.
**Freshness semantics:** validator checks source `retrieved_at <= sourceCutoffAt` and `published_at <= evaluationAsOf`; it rejects `fresh_until > retrieved_at + freshness_seconds` and ignores facts whose `fresh_until < evaluationAsOf`. It does not itself prove issuer financial reporting period is current, and retrieval date is NOT the reported period. An explicit `supersedes_review_id` chain controls which reviewed fact is active; branched/invalid review chains are rejected, while same-period observations with inconsistent facts cannot silently overwrite each other.
**Policy mismatch:** initial fresh-days caps of 120 days for M1/M2/M3 and 90 days for M4 were not specified in the owner decision. Read-only check of selected `research_evidence_snapshot_items` found 179 rows per requirement with `freshness_policy=null` for all four. The existing 150/550-day documentary example is not sufficient to infer a universal policy for these numeric BANK metrics.
**Corrective fail-closed DB data update:** kept all four registry records and their direct semantic metadata, but set `is_active=false`, `definition.activation_status=BLOCKED_PENDING_EXPLICIT_FINANCIAL_FRESHNESS_POLICY`. This prevents unapproved 120/90-day caps from functioning as an accepted readiness policy. Existing values are retained only for audit, not approved for activation. No schema change, review deletion or readiness mutation. To activate, the owner must approve a per-family expiry policy with both reporting-age and source-retrieval clock, reviewed period overlap and supersession details; update through established metric registration path followed by regression tests.
